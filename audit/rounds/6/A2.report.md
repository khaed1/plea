## Findings

### 1. Low: PleaLaunch's constructor accepts a zero (or swapped) Letterbox code hash: deployLetterbox is then impossible for every input and seed refuses LetterboxNotDeployed for good, after PLEA has minted the 8

`src/PleaLaunch.sol:108`

```
        letterboxCodeHash = letterboxCodeHash_;
```

R5-A2-1 moved the Letterbox's chain-independent refusals (OracleAssetNotImd, MintWithPoolImd, OracleAssetMismatch) into PleaLaunch's constructor so that a launch whose letters can never work is refused inside the launch transaction (THREAT-MODEL invariant 17 and section 3). The 12th argument, letterboxCodeHash_, is stored without any check. keccak256 of any creation code is never zero, so with bytes32(0) deployLetterbox reverts WrongInitCode for every input, and since round 5 seed reverts LetterboxNotDeployed until a Letterbox exists. The launch still registers itself with PLEA (setLauncher) and deployHook still mints 82% to the hook, 6% to Seasons and 12% to the distributor; trading never opens, PLEA stays restricted forever (gate.startedAt == 0), the distributor's claims pay into wallets that can never move, and nothing can be redeployed (PLEA.setLauncher is once). The same slip exists for arguments 12 and 13 swapped: the constructor accepts it, deployLetterbox would then accept the Tribunal's creation code, and deployTribunal the Letterbox's. A zero value is a plausible operator error because the very next argument (tribunalCodeHash_) uses zero to mean 'objections off'. No user IMD is at risk (trading never opens) and launch.json carries the correct hash at this commit (test/LaunchManifest.t.sol test_launchJsonCommitsToThisLetterbox pins it), so this is a missing check with no impact today: Low. Merged from the economics and math specialists (both reproduced). Fix, one comparison in the constructor beside the three oracle-fee refusals: if (letterboxCodeHash_ == bytes32(0) || letterboxCodeHash_ == tribunalCodeHash_) revert WrongInitCode(); (a zero Tribunal hash stays the documented 'objections off'). Invariant 17 checked: the committed-code deployments, CREATE2 addresses, once-each rules, the mint split and the seed order all hold otherwise (test/Launch.t.sol, test/LaunchManifest.t.sol, 78 area tests green).

**Reproduction**

Deploy PLEA(owner) and a gate stub whose oracleAsset() is the IMD address, then new PleaLaunch(plea, gate, seasons, distributor, pm, imd, stacker, 1_300_000, start, imd, false, bytes32(0), bytes32(0)) (the mainnet fee settings; the Sepolia ones behave the same). Expected: the constructor reverts, as it does for OracleAssetNotImd / MintWithPoolImd / OracleAssetMismatch. Actual: it deploys and registers itself as PLEA's launcher; deployLetterbox(type(Letterbox).creationCode) reverts WrongInitCode (as does every other input) and seed() reverts LetterboxNotDeployed forever once a hook exists (both specialists' proofs run here: Proof_6dbbf18d8a2d fails 'PleaLaunch accepted a zero Letterbox code hash', Proof_a8d20d56c330 fails 'next call did not revert as expected'). test/scratch/ZeroLetterboxHash.t.sol: test_theLaunchRefusesAZeroLetterboxHash fails on this code with 'next call did not revert as expected' and test_theRealLetterboxHashDeploys shows the same settings with the real hash deploy and predictLetterbox() matching.

### 2. Info: seed waits for the Letterbox but not for a committed Tribunal: trading can open with tribunal() == 0, and a plea approved and recorded in that gap can never be objected to

`src/PleaLaunch.sol:196`

```
        if (letterbox == address(0)) revert LetterboxNotDeployed();
```

R5-A2-1 made seed refuse LetterboxNotDeployed so that trading never opens on a launch whose letters cannot work. The same rule is not applied to the Tribunal when the launch committed to one (tribunalCodeHash != 0, as launch.json does): seed succeeds while tribunal == address(0). deployTribunal and seed are both permissionless from START (and the owner may seed any time), so the order is whoever is first. While no Tribunal exists Seasons._standing is fail-open (invariant 10: no hold), so a plea approved in the gap is recorded at once (the Letterbox's _deliver / _settle call record, or anyone does), and once recorded Tribunal.object refuses it for good (AlreadyRecorded). Nothing is lost permanently (anyone deploys the Tribunal later, the window is 20 minutes, and OBJECTIONS.md's rule 'not yet recorded in Seasons (this covers pleas recorded before the Tribunal existed)' already anticipates the state), so this is a consistency gap with invariant 17's Letterbox rule, not a loss: Info, as the permissions specialist rated it. Fix, if wanted (no agreed number changes): in seed, if (tribunalCodeHash != bytes32(0) && tribunal == address(0)) revert TribunalNotDeployed(); the deployer then runs deployTribunal before seed, as script/Deploy.s.sol already does.
