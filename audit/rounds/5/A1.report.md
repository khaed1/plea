## Findings

### 1. Medium: One sham objection filed in the window's last second shields a plea from every rival: the second ruling slot is unreachable

`src/Tribunal.sol:246`

```
        if (block.timestamp > uint256(verdictAt) + OBJECTION_WINDOW) revert WindowClosed(pleaId);
```

Merged from the economics specialist; reproduced by the judge on the project fixture (test/scratch/LastSecondShield.t.sol, three variants: overruled, void, stale). `object` refuses any filing after verdictAt + 20 min (line 246) and any filing while a non-stale objection is pending (lines 251-253). A pending objection goes stale only after its own 20-minute PENDING_EXPIRY or an Intake completion. So an objection filed in the last seconds of the window occupies the only pending slot until the window has closed: every other wallet gets ObjectionPending until verdictAt + 20 min and WindowClosed afterwards, whatever the sham's outcome (overruled, void or stale). The case ends with count <= 1 and the second ruling slot can never be used. More generally a sham filed at time t blocks rivals for min(panel latency, 20 min, window remaining), so with a slow panel one sham filed mid-window shields the rest of it. OBJECTIONS.md Decisions says the cap was raised from one to two precisely so that 'the seller's second wallet' cannot 'file a harmless objection first and shield the plea' and that 'two rolls still bound a rich rival'; THREAT-MODEL section 3 and Known limit 1 accept only the two-sham shield (1.7 IMD, two re-rolls of the seller's own score). The timed variant costs 0.85 IMD and exposes the seller to one re-roll, with text the seller writes. Invariant 11 is not broken (the code does what it says), the design's stated reason for MAX_OBJECTIONS = 2 is. Borderline Low: the shield itself is an accepted limit and a rival who files early is not blocked; the owner may accept it in writing as an extension of Known limit 1. Fix options that keep every agreed number: (a) let a second objector file while one objection is pending, with a per-case pending count so that pending + ruled <= MAX_OBJECTIONS and the different-wallet rule checked against the pending objector too (both still filed inside the 20-minute window and each expiring 20 minutes after filing, so the 40-minute bound inside the 60-minute close grace holds); or (b) extend the rival's window by the time a pending objection occupied it, capped so the last ruling still ends inside CLOSE_GRACE.

**Reproduction**

Fixture with the Tribunal on (withTribunal = true), alice approved at score 40 at time V. 1) vm.warp(V + 20 minutes): accomplice calls tribunal.object(id, text): accepted, caseOf(id).pendingId = sham. 2) Same second, rival calls tribunal.object(id, text): reverts ObjectionPending(sham). 3) Five minutes later the Intake rules the sham (40, overruled), or fails it (void), or nobody answers (stale after 20 more minutes): in every case rival's object(id, text) reverts WindowClosed(id). 4) caseOf(id).count <= 1; after the hold seasons.record(id) records 40 points, bestOf(0, alice)[0] == 40. Expected per OBJECTIONS Decisions / Known limit 1: one sham spends one of two rulings and a rival keeps the other. Actual: no rival can ever object. Run: forge test --match-path test/scratch/LastSecondShield.t.sol (the sequence passes as described in all three variants).

### 2. Low: Profit bands are floor-rounded: a gain just above 50% / 200% / 500% / 1,000% scores the better band, up to 2 need points off the agreed table

`src/CabalGate.sol:284`

```
                uint256 gainPct = (value - spent) * 100 / spent;
                score += gainPct <= 50 ? 12 : gainPct <= 200 ? 10 : gainPct <= 500 ? 8 : gainPct <= 1000 ? 6 : 4;
```

Merged from the math specialist; the attached proof fails on this code exactly as stated (33 != 31 at the 50% edge, 31 != 29 at the 200% edge). _factScoreAt computes the gain as a whole percent rounded down and compares it with <= 50 / 200 / 500 / 1000, so every gain inside (50%, 51%) scores the <=50% band (12 instead of 10), inside (200%, 201%) the <=200% band (10 instead of 8), and the same at 500% and 1,000%: the seller's need is 2 points lower than THREAT-MODEL invariant 3 and README line 117 ('gain <=50%: 12 . <=200%: 10 . <=500%: 8 . <=1,000%: 6 . more: 4') say, on a band of almost one percentage point at each edge. The run-7 profit table is new (FINDINGS 'Changes after run 7'); R1-A1-3 accepted floor rounding only for the share bands, whose basis-point comparison leaves an edge a hundred times narrower (0.01%). No value moves and the effect is bounded (2 need points, only inside four 1%-wide gain bands), so Low; a changed agreed number only at the edges, at the owner's discretion. Fix (no extra bytes needed): compare without the division, e.g. `uint256 g = value - spent; score += g * 2 <= spent ? 12 : g <= spent * 2 ? 10 : g <= spent * 5 ? 8 : g <= spent * 10 ? 6 : 4;`, or document the whole-percent floor in invariant 3.

**Reproduction**

basisOf(seller) = (spent 100 IMD, heldPlea 1,000,000 PLEA, bought now); latestPrice = price24hAgo = 150.9 IMD per 1,000,000 PLEA (a 50.9% gain, flat trend); balance 1,000,000 PLEA; factScore(seller, 100,000 PLEA) (10% share). Expected 16 + 0 + 10 + 5 = 31 (need 40); actual 33 (need 38). At 300.9 IMD (a 200.9% gain): expected 29, actual 31. Run: forge test --match-path test/scratch/ProfitBandEdge.t.sol (both tests fail on this code).

**Proof**: a Foundry test that fails on this code and passes once it is fixed.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.26;

import "forge-std/Test.sol";
import {CabalGate} from "src/CabalGate.sol";

contract MockPlea {
    address public hook;
    mapping(address => uint256) public balanceOf;
    constructor(address h) { hook = h; }
    function setBal(address a, uint256 b) external { balanceOf[a] = b; }
    function launcher() external pure returns (address) { return address(0); }
}

contract MockHook {
    uint256 spent; uint256 held; uint256 since; uint256 price;
    function set(uint256 s, uint256 h, uint256 t, uint256 p) external { spent = s; held = h; since = t; price = p; }
    function basisOf(address) external view returns (uint256, uint256, uint256) { return (spent, held, since); }
    function latestPrice() external view returns (uint256) { return price; }
    function price24hAgo() external view returns (uint256) { return price; } // flat: +5
}

contract ProfitBandEdgeTest is Test {
    uint256 constant Q96 = 2 ** 96;
    MockHook h;
    MockPlea p;
    CabalGate g;
    address seller = address(0xBEEF);

    function setUp() public {
        vm.warp(1_000_000);
        h = new MockHook();
        p = new MockPlea(address(h));
        g = new CabalGate(address(p), address(1), address(2), address(3), address(4), 5 hours, 33 hours);
        p.setBal(seller, 1_000_000e18);
    }

    /// Bought 1,000,000 PLEA for 100 IMD; the checkpoint values it at 150.9 IMD: a 50.9% gain.
    /// The agreed table (THREAT-MODEL inv. 3) gives "gain <=50%: 12, <=200%: 10", so a 50.9% gain
    /// must score 10 profit points. The fact score must be share 16 + hold 0 + profit 10 + trend 5 = 31.
    function test_aGainJustAbove50PercentScoresTheTwoHundredBand() public {
        uint256 price = 1509 * Q96 / 10_000_000; // 150.9 IMD per 1,000,000 PLEA
        h.set(100e18, 1_000_000e18, block.timestamp, price);
        uint8 f = g.factScore(seller, 100_000e18); // 10% share: 16
        assertEq(f, 16 + 0 + 10 + 5, "a 50.9% gain scored the <=50% band");
    }

    /// Same at the 200% edge: a 200.9% gain must score 8, not 10.
    function test_aGainJustAbove200PercentScoresTheFiveHundredBand() public {
        uint256 price = 3009 * Q96 / 10_000_000; // 300.9 IMD per 1,000,000 PLEA
        h.set(100e18, 1_000_000e18, block.timestamp, price);
        uint8 f = g.factScore(seller, 100_000e18);
        assertEq(f, 16 + 0 + 8 + 5, "a 200.9% gain scored the <=200% band");
    }
}
```
