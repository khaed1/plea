# Audit report

> PLEA security audit, round 1, area A1: The game: gate, Tribunal, seasons. PLEA is a sell-gated meme token on Uniswap v4 paired with IMD: anyone buys, selling needs a plea judged by a 30-seat IdentityMD oracle panel, approved pleas score season points for IMD and PLEA prizes, and every trade pays cashback in staked IMD through imd/acc's Stacker. Solidity 0.8.26, Foundry (cancun, via-IR), a Uniswap v4 hook, IdentityMD Intake v2 callbacks. This is the mainnet code, rehearsed first on Sepolia (launch.json on this commit has the Sepolia settings). Other areas of the same commit are audited by separate jobs; stay on this one.

> Context: CabalGate takes pleas and appeals, computes the fact score and the need from the hook's hourly checkpoints, pays the 0.5 IMD fee to the Intake with the question, checks the signed verdict (OracleAttestation: EIP-712 then ERC-1271, panel 30, quorum 17, score 0-45) in the Intake's callback, and runs the 7-minute gated sale through the hook; the dead-man (33 hours without a verdict) ends the game. The Tribunal is Objection!: for 20 minutes after an approval a second panel may re-score the plea (0.5 IMD fee + 0.35 IMD stake), sustained when newScore + 2 < need, otherwise overruled, void on no answer; at most two rulings per plea from different wallets. Seasons records each approved plea's min(original, lowest re-score) as points, times 1.2 when the seller holds an IMD seat NFT at record time (run 7), keeps each wallet's best three, pays the top 25 with 60+ points from 450 down to 350 bps of the season pot and the 10,000,000 PLEA bonus in each of the first six seasons, excludes the owner and the launch owner, and flushes what is left to the buy wall after the death.

## Findings

### 1. Low: Permissionless record lets any address fix the seat-multiplier moment: a rival records a plea while the seller holds no seat and the 1.0x points are permanent (merges audit_math 22254db8 and audit_eco

`src/Seasons.sol:219`

```
    function record(uint256 pleaId) external {
```

THREAT-MODEL section 3 accepts that the seat NFT is read at record time with the justification 'record is permissionless, so the seller chooses the moment'. The second half is not what the code does. record(pleaId) has no caller check and _record reads holdsSeat(seller) in the recording transaction only (line 260), so the FIRST caller fixes the multiplier, not the seller. Anyone watching Verdict events can call record the second a plea becomes recordable (verdictAt + 20 minutes + 1 s with the Tribunal, or at the verdict without one; or when a pending objection is ruled or goes stale), and the Letterbox's deliver/settle and a closeSeason id list do the same. recorded[pleaId] is then true forever and the plea counts score x 1.0 instead of x 1.2 (45 -> 54 lost, 9 points per plea, up to 27 over the best three), which can decide a top-25 rank or the 60-point bar. A seller who keeps a seat in the selling wallet from the verdict on is unaffected; a seller who holds the seat in another wallet, or planned to acquire or borrow one for the record (the accepted borrowed-seat path), is stripped at gas cost to the rival. Points-only griefing, so Low under section 4; Medium is arguable if the borrowed-seat path is meant to be supported since the attacker's cost (gas) is below the victim's loss. Fix options that keep the design: let only the seller (and the Letterbox for its escrows) record inside a short grace after the hold ends, others afterwards; or read the seat at the verdict (onOracleResult stores a flag) instead of at record time. At minimum correct THREAT-MODEL section 3 and the README so seat holders know the first caller fixes the multiplier. Invariants checked: 7 (recorded once, by anyone, after the hold), 10 (seat read fail-open).

**Reproduction**

Fixture (test/utils/Fixture.sol) with withTribunal() = true; alice, bob, carol each buy 50 IMD of PLEA, skip 1 day. alice: approvedPlea(alice, 45) (10% plea, need 40, approved at 45). skip(20 minutes + 1). vm.prank(bob); seasons.record(id) succeeds: seasons.recorded(id) == true, seasons.bestOf(0, alice)[0] == 45. Then seat.mint(alice): seasons.pointsFor(alice, 45) == 54, but vm.prank(alice); seasons.record(id) reverts AlreadyRecorded(id) and bestOf(0, alice)[0] stays 45. Expected per THREAT-MODEL section 3: the seller picks the recording moment and can record with the seat for 54. Actual: bob picked it and alice has 45 for good. Reproduced in test/scratch/A1Judge.t.sol test_rivalRecordsBeforeTheSellerHoldsASeat (passes on this code, i.e. the strip succeeds).

### 2. Low: A lapsed approval's 4-hour cooldown is dated from the verdict, not from the lapse, and the README's outcome table lists no cooldown for a lapse at all (merges audit_flow 7ed94c64 and audit_economics 0

`src/CabalGate.sol:464`

```
            lastLapsedAt[seller] = p.verdictAt;
```

THREAT-MODEL invariant 5 says 'a sale, a denial or a lapse starts a 4-hour cooldown'. A sale stamps block.timestamp (_sell, lastExecutedAt) and a denial stamps the verdict time (onOracleResult, lastDeniedAt), but _clearStale stamps a lapse with p.verdictAt, which is 7 minutes (EXECUTE_WINDOW) before the window actually lapsed, so the lapse cooldown ends at verdictAt + 4h, i.e. 3 hours 53 minutes after the lapse; a seller who sells at the last second of the window waits 7 minutes longer than one who lets it lapse. README.md line 65 ('Approved, not sold in 7 min | Lapsed; the score still counts for the season') promises no cooldown at all, while the code and the Letterbox's cooldown display (Letterbox.sol line 615) apply one. Three documents say three different things (no cooldown / 4h from the lapse / 4h from the verdict). No value is at risk and the lapsed approval cannot be executed, so Low (user-facing behaviour that the README contradicts). Fix: either stamp block.timestamp (if the agreed number is 4 hours from the lapse) or state in the README table and THREAT-MODEL that a lapse starts the 4-hour cooldown measured from the verdict; test/GateAdversarial.t.sol line 73 currently asserts the verdict stamp, so the fix changes that assertion too. Invariant checked: 5.

**Reproduction**

Fixture with the Tribunal, alice has bought 50 IMD of PLEA and held 1 day. approvedPlea(alice, 45) at time V (verdictAt = V). skip(8 minutes) (the window lapsed at V + 7 min). vm.prank(alice); gate.submitSell(small(alice), 'again') reverts Cooldown(V + 4 hours), not Cooldown(V + 7 minutes + 4 hours) and not success as the README table implies. vm.warp(V + 4 hours): the same call succeeds, gate.getPlea(id).status == Lapsed and gate.lastLapsedAt(alice) == V. Reproduced in test/scratch/A1Judge.t.sol test_lapseCooldownRunsFromTheVerdict.

### 3. Info: Seasons.Recorded reports points = 0 when the plea does not enter the wallet's best three (merges audit_math f27f533a and audit_flow c8898cbe)

`src/Seasons.sol:279`

```
        emit Recorded(pleaId, season, seller, score, pts);
```

uint16 pts is declared before the replacement branch of _record and assigned only inside it. When the new plea's points do not beat the wallet's lowest counted plea (fewer points, or equal points with a higher plea id), the branch is skipped, recorded[pleaId] is still set, and the event carries points == 0 as the wallet's season total. Stored state (_best, _top) is untouched and correct; an indexer or the site's leaderboard reading Recorded.points as 'the wallet's points after this record' sees the wallet drop to 0. Display only. Fix: initialise pts to b[0] + b[1] + b[2] before the branch (or document that the field is zero when nothing changed).

**Reproduction**

Fixture without a Tribunal; alice buys 50 IMD of PLEA, skips 1 day, then gets four approved 10% pleas 4 hours apart (each submitted at the previous verdict + 4h, scores 45, 45, 45, 44; needs 40 or less). seasons.record of the first three sets topOf(0)[0] = (alice, 135). seasons.record(fourthId) emits Recorded(fourthId, 0, alice, 44, 0) (vm.expectEmit with the zero-points event passes) while topOf(0)[0].points is still 135. Expected: the event reports 135 or documents the zero. Reproduced in test/scratch/A1Judge.t.sol test_recordedEventSaysZeroPointsWhenNotCounted.

### 4. Info: The judges' question prints 'sell 0 PLEA' for a plea below one PLEA (a small holder's 1% minimum is under one token) (audit_flow aa2787d6)

`src/CabalGate.sol:679`

```

```

_question prints the plea amount as whole PLEA with integer division. _checkAmount accepts any amount of at least 1% of the balance, so a holder of fewer than 100 PLEA (a tiny buy, a small airdrop leaf, a prize share) may plead 0.5 to 0.99 PLEA and the panel of 30 reads 'sell 0 PLEA'; the Tribunal quotes this question verbatim for objections. Display only: the sale, the fact score and the points use p.amount exactly. Fix: print one or two decimals, or 'less than 1 PLEA'.

### 5. Info: Fact-score band edges are floor-rounded: shares in [15%, 15.01%) and [30%, 30.01%) and gains in [50%, 51%) and [200%, 201%) score the better band (audit_math 7c81b0d9)

`src/CabalGate.sol:261`

```
        score = shareBps <= 1_500 ? 16 : shareBps <= 3_000 ? 9 : 3;
```

shareBps = amount * 10_000 / bal truncates, so any share in [15%, 15.01%) is 1500 bps and scores 16 rather than 9 (likewise 30%); gainPct = (value - spent) * 100 / spent truncates, so a gain in [50%, 51%) scores 8 instead of 3 and [200%, 201%) scores 3 instead of 0. The slack is one basis point of the balance and one percentage point of gain, inside the panel's noise and the table's 'at most 15%' intent, so no realistic effect on the need; noted because the agreed table is stated with exact edges. If exact edges are wanted compare without division: amount * 10_000 <= bal * 1_500 and (value - spent) * 100 <= spent * 50.

**Reproduction**

Fixture: alice holds bal PLEA. gate.factScore(alice, bal * 1500 / 10_000) == gate.factScore(alice, bal * 1500 / 10_000 + bal / 20_000) (about 15.005% of the balance) and both are 7 points above gate.factScore(alice, bal * 1501 / 10_000 + 1). Expected under a strict '<= 15%' edge: the 15.005% plea scores the 9-point band. Reproduced in test/scratch/A1Judge.t.sol test_factScoreShareBoundary.

### 6. Info: Seasons.pointsFor truncates scores above 213 for a seat holder (view only; _record never passes more than 45) (audit_permissions 4e05f9b1)

`src/Seasons.sol:132`

```
        return holdsSeat(wallet) ? uint8(uint256(score) * SEAT_MULTIPLIER_BPS / 10_000) : score;
```

pointsFor(wallet, score) is public and takes any uint8; for a seat holder the product is cast to uint8 without a bound, so a score above 213 wraps (214 -> 256 -> 0, 255 -> 306 -> 50). No on-chain path is affected: _record only passes the judged score (0-45, capped by ScoreOutOfRange in the gate and the Tribunal), so recorded points stay in 0-54 per plea and 162 for three, and the uint8/uint16 bounds hold. Display-only; a `require(score <= MAX)` or a uint16 return would make the view total.

**Reproduction**

Fixture: seat.mint(alice). seasons.pointsFor(alice, 214) returns 0 (expected 256 or a revert); seasons.pointsFor(alice, 255) returns 50 (expected 306); seasons.pointsFor(bob, 255) with no seat returns 255. Reproduced in test/scratch/A1Judge.t.sol test_pointsForTruncatesAbove213.
