## Findings

### 1. Low: The 14,000 IMD mainnet opening market cap is a compile-time constant (5,700 on this commit) that PleaLaunch.seed's chain-1 guard never checks

`src/PleaHook.sol:86`

```
    uint256 public constant MARKET_CAP_IMD = 5_700e18;
```

Invariant 20 fixes the opening market cap at 5,700 IMD on Sepolia and 14,000 IMD on mainnet. The value is a constant baked into PleaHook's creation code (which PleaLaunch commits to by hash), so the same build cannot serve both chains, and the only thing telling the two apart is which branch is built. PleaLaunch.seed (src/PleaLaunch.sol:208) refuses the Sepolia SEASON / DEADMAN on chain id 1 with BelowAgreedTiming, but has no equivalent check for IPleaHook(hook).MARKET_CAP_IMD(): this commit's manifest deployed on chain id 1 with the agreed clock seeds at ~5,720.83 IMD without complaint. Judge's correction of the specialist's premise: origin/mainnet is now 9f96deb, a merge of `next` whose merge-base with this commit is this commit itself, so the mainnet branch already carries both round-7 hook fixes and differs from this tree only by the one-line constant (`git diff 02407c1 origin/mainnet -- src/PleaHook.sol`). The merge risk the specialist described no longer exists; what remains is a missing on-chain check with no impact today (severity scale: Low). Fix: in PleaLaunch.seed's chain-1 branch add `IPleaHook(hook).MARKET_CAP_IMD() < 14_000e18` to the BelowAgreedTiming condition (and a view to IPleaHook), or make the cap a PleaLaunch constructor argument checked there; no agreed number changes.

**Reproduction**

Reproduced with test/scratch/Round8A3Judge.t.sol `Round8A3ChainOneSeedTest.test_chainOneSeedOpensAtTheSepoliaMarketCap`: the fixture's manifest (SEASON 15 days, DEADMAN 33 hours, oracle fee = pool IMD) deployed under vm.chainId(1); the owner calls PleaLaunch.seed(). Expected: a refusal (as BelowAgreedTiming for the clock) or a pool at >= 14,000 IMD. Actual: seed succeeds, hook.MARKET_CAP_IMD() == 5_700e18 and priceX96 * 1e9 supply / 2^96 is between 5,700 and 5,760 IMD. PASS.

### 2. Info: A Stacker address without code is not covered by the plain-IMD cashback fallback: the extcodesize revert happens outside the try, so every cashback-paying swap reverts

`src/PleaHook.sol:757`

```
        try stacker.credit{gas: creditGas}(trader, amount) {
```

IStacker.credit returns nothing, so Solidity 0.8.26 emits an extcodesize check before the external call; it reverts in the hook's own frame, before the try, and is not caught. The NatSpec (lines 748-751) and THREAT-MODEL invariant 19 promise plain IMD 'if the credit reverts'; with a Stacker that has no code the hook reverts with empty data inside afterSwap, the PoolManager wraps it (HookCallFailed) and the swap fails. Reachable only through launch configuration: the constructor deliberately tolerates a codeless Stacker (_vaultOf returns zero so IMD's chain-id-1 rehearsal passes with a placeholder), and after Cancun a deployed Stacker's code cannot vanish, so with the live imd/acc Stacker in launch.json nothing happens. If the address were wrong or not yet deployed, every buy with a resolvable trader (all buys while the Cabal lives) would revert from the first trade. Fix (either keeps the agreed design): check address(stacker).code.length != 0 in _payCashback and take the plain-IMD path when it is zero, or document that the fallback covers a reverting credit only and add the Stacker code check to the launch checklist.

**Reproduction**

Reproduced with test/scratch/Round8A3Judge.t.sol `test_codelessStackerRevertsEveryCashbackSwap`: default fixture, alice buys 2,000 IMD; control: stacker.setBurnAllGas(true) and bob's 100 IMD buy pays plain IMD (balance above before - 100 IMD). Then vm.etch(address(stacker), "") and carol's router.buyExactIn(100e18, abi.encode(carol)). Expected per NatSpec: CashbackPaidPlain. Actual: the buy reverts. PASS (vm.expectRevert).

### 3. Info: totalBurned omits the seed's dust burn, so totalSupply + totalBurned is under the minted supply by about 820 PLEA forever

`src/PleaHook.sol:415`

```
        if (dust != 0) IPLEA(plea).burn(dust);
```

seed() burns the PLEA the single-sided position's 1e-6 rounding margin leaves behind (~820 PLEA of the 820M) without adding it to totalBurned, while every later burn (_burnPlea: the 0.25% sale fee, trims, settled walls, redeemed PLEA claims) does. The identity supply + totalBurned == 1,000,000,000 PLEA therefore never holds from the seed on; the project's own suites measure from the post-seed sum (test/HookAdversarial.t.sol, test/Token.t.sol, test/HookRevision.t.sol:409). No funds move; display/accounting only. Fix: `totalBurned += dust;` beside the burn in seed().

**Reproduction**

Reproduced with test/scratch/Round8A3Judge.t.sol `test_seedDustIsBurnedButNotCounted`: after the fixture's launch.seed(), hook.totalBurned() == 0 and 1_000_000_000e18 - (plea.totalSupply() + hook.totalBurned()) is between 800 and 900 PLEA (the dust that was burned). Expected 0. PASS.

### 4. Info: pendingRebalance() stays true while rebalance() reverts RebalanceNotNeeded in a drained pool (keeper view mismatch)

`src/PleaHook.sol:337`

```
        return retainedImd + retainClaims >= WALL_THRESHOLD || pleaInWall() >= WALL_MIN_FILL || pleaClaims != 0;
```

After the Cabal's death a price-limited exact-input sale can leave spot more than one tick spacing beyond refTick on the IMD side with no active liquidity (the accepted R1-A3-3 state). With no wall, no claims and retainedImd >= WALL_THRESHOLD, _rebalance returns (0, false) at line 877 (`if (amount == 0 || drained) return (work, acted);`), so rebalance() reverts RebalanceNotNeeded, but pendingRebalance() keeps returning true because it never reads the drained condition. A keeper that polls the view (the documented keeper-bot pattern) sends a reverting transaction on every poll until a buy restores spot. No funds are affected; the reserve stays in the hook as retainedImd. Fix: have pendingRebalance() return false when the drained condition holds and neither claims nor a filled wall are due (or expose the drained flag).

**Reproduction**

Reproduced with test/scratch/Round8A3Judge.t.sol `test_pendingRebalanceTrueWhileRebalanceRevertsWhenDrained`: alice buys 100 IMD; the Cabal dies; alice receives 50M PLEA from the distributor and sells it exact-input through the plain router with a limit 2,000 ticks beyond the market band on the IMD side (pool liquidity 0 afterwards); fundWall(1e18). A first rebalance() redeems the 0.25 IMD of pool-share claims (acts) and deploys no wall. Now retainClaims == 0, pleaClaims == 0, wall liquidity 0, retainedImd >= 1 IMD. Expected: pendingRebalance() == false or rebalance() does work. Actual: pendingRebalance() == true and rebalance() reverts RebalanceNotNeeded. PASS.

### 5. Info: After the death a router can flash-take the PoolManager's PLEA and turn its own swap's 0.25% burn (and any trim) into deferred PLEA claims; harmless, burned at the next rebalance

`src/PleaHook.sol:640`

```
        if (IERC20(plea).balanceOf(address(poolManager)) < amount) {
```

Check of the R7-A3-1 fix for new paths. _burnPlea decides between take-and-burn and minting ERC-6909 PLEA claims from the PoolManager's live ERC-20 PLEA balance, unlike the IMD side (R3-A3-1), which keys on the pool's own IMD before the swap. Once the Cabal is dead PLEA transfers are free, so a router may, inside its own unlock, take the PoolManager's whole PLEA balance, swap, and settle the PLEA back; during that swap every _burnPlea call (the 0.25% fee, a trim, a wall settle inside rebalance is not reachable this way) mints pleaClaims instead of burning. The claims are fully backed, anyone burns them with rebalance() (pendingRebalance turns true), supply + totalBurned is conserved and nobody loses value; the effects are a lag in totalBurned and an unpaid rebalance() call. While the Cabal lives the path is closed: the router cannot settle PLEA back into the PoolManager (PLEA._update refuses to == poolManager unless from is the gate or the hook). Not a defect of consequence; a cheap hardening is to key the check on the PLEA this pool owns (market + wall PLEA at priceBefore) like the IMD side, or to note it under THREAT-MODEL section 3.

**Reproduction**

Reproduced with test/scratch/Round8A3Judge.t.sol `test_flashTakenPleaTurnsTheBurnFeeIntoClaims` (FlashTakePleaRouter in the same file): Cabal dead; the router's unlockCallback does pm.take(plea, router, plea.balanceOf(pm)), then an exact-input buy of 100 IMD with hookData = abi.encode(bob), settles the IMD and settles the PLEA it took back minus bob's output. Expected (the IMD-side rule): the swap reverts at the hook's take. Actual: the buy fills, hook.pleaClaims() equals the buy's 0.25% PLEA fee (got * 25 / 9975 within 1e-6), totalBurned is unchanged, and rebalance() then burns exactly that amount with supply + totalBurned conserved; the same buy through the plain router burns inside the swap. PASS.
