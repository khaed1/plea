## Findings

### 1. Low: APPEAL by letter is refused FeeTooHigh after a small price dip: the R1-A2-3 exception compares the appeal's fees with the original plea's PLEA amount, fixed at the plea's higher snapshot (mainnet fee

`src/Letterbox.sol:348`

```
        if (maxFeePlea * BPS > bal * MAX_FEE_SHARE_BPS && maxFeePlea > originalAmount) {
```

Mainnet fee path (the oracle fee is bought in pool IMD). A letter needs 0.825 IMD of fees (0.75 IMD + 10%) to fit 10% of the balance, so the smallest letter writer holds about 8.25 IMD of PLEA at the plea's snapshot and pleads 15% of it. An APPEAL letter buys 1.21 IMD of fees (1.1 IMD + 10%) priced at the appeal's snapshot. The exception on line 348 (the R1-A2-3 fix) lets those fees exceed 10% of the balance only while maxFeePlea <= originalAmount, where originalAmount is a PLEA amount fixed at the plea's price. When the hourly checkpoint has fallen by more than about 2.3% between the letter and the appeal (inside the 4-hour appeal window), 1.21 IMD costs more PLEA than the original plea's amount and more than 10% of the shrunken balance, so _appeal reverts FeeTooHigh. README 'Pleading by letter' and the comment above line 348 say whoever could plead by letter can always appeal by letter; the code guarantees it only at a flat or rising price, so the R1-A2-3 fix is incomplete under a dip. No funds are at risk: the denied letter's escrow and tip come back through settle; the writer may still appeal at the gate with 0.85 IMD of their own (which a letter writer may not hold). Invariant 15 checked: the written bounds (+10%, 10% of the balance, or the original plea's amount) are enforced; only the README's consequence fails. Fix that keeps the agreed bounds: compare the appeal's fees with the original plea's amount valued at the appeal snapshot with the same +10% slack (i.e. originalAmount * priceAtPlea / priceNow), or with the greater of originalAmount and 10% of pleaBalance[originalId]; or document the price condition in the README. Merged from audit_economics bb3f33a3; reproduced with the specialist's proof.

**Reproduction**

test/scratch/AppealBandByLetter.t.sol (mainnet fee path: oracleFeeToken() = imd). Five funded wallets buy 150 IMD each, alice buys 8.45 IMD; a day later a 1 IMD buy sets the hour's checkpoint and alice's PLEA is worth 8.25-8.7 IMD. alice's raw letter 'Fifteen percent for the phone bill; the rest stays with me.' is accepted (fees fit 10%) and answered 0 (denied). Expected (README): the appeal is escrowed. Actual: the call reverts Letterbox.FeeTooHigh. `forge test --match-path test/scratch/AppealBandByLetter.t.sol` fails on this commit with 'whoever could plead by letter should be able to appeal by letter' (run by the judge: FAIL as stated).

### 2. Info: plead(amount) with an amount above the balance minus the fee reserve reverts in the token (ERC20InsufficientBalance) instead of the gate's AmountTooLarge

`src/Letterbox.sol:297`

```

```

_plead escrows amount + maxFeePlea through PLEA.courtTake before the gate's _checkAmount(amount, balance) runs inside submitFor. A 15% letter and any site plea at or under the gate's 50% ceiling always fit (50% + 10%), so this shows only when the site's box asks for more than the balance minus the fee reserve: the writer gets the token's ERC20InsufficientBalance instead of AmountTooLarge. ### 4. Info: A buy naming the Letterbox as trader delivers the bought PLEA into the Letterbox (its holdings exceed its open escrows; a harmless sink reached through the hook)

`src/PLEA.sol:137`

```

```

Invariant 14 says the Letterbox holds exactly its open escrows plus one tip each 'and nothing else', and PLEA._update refuses direct sends to the Letterbox. The hook's buy delivery (poolManager.take(plea, trader, ...)) is a transfer from the PoolManager, an exempt sender, to the trader any router caller names through hookData = abi.encode(trader); naming the Letterbox lands the PLEA there (the letterbox-only clause is never reached because _exempt(from) is true) and the hook records a buy history for the Letterbox. Naming the gate reverts (to == gate needs msg.sender == gate). The PLEA is unreachable (the Letterbox reads only escrow amounts, never its balance), so no writer's escrow or tip is affected and nothing can be extracted: THREAT-MODEL section 3 'Sinks' reached through the hook at the buyer's own cost. Reported because the wording of invariant 14 ('nothing else') and the LetterboxInvariant harness assume the balance equals the sum of open escrows, which a stranger can break for one wei of IMD. Either reword invariant 14 to 'at least', or have the hook refuse the system contracts as a named trader. Merged from audit_permissions 9c47c6fc.

### 5. Info: settle returns a tip bought with PLEA: an unapproved, lossy PLEA-to-IMD exit of 0.25 IMD per letter, every 20 minutes when no verdict comes

`src/Letterbox.sol:439`

```
        imd.safeTransfer(writer, TIP);
```

Invariant 15 lets the gate sell the writer's PLEA for the fees (0.75 IMD on mainnet, at most +10%) and invariant 14 returns the tip on every non-sale ending. Together they are a sell channel that needs no approval: each letter converts about 0.765 IMD worth of PLEA into 0.25 IMD in the writer's wallet, the rest spent on the Intake. A denial costs a 4-hour cooldown, but a plea the panel never answers (expired after 20 minutes, or the Intake's failure callback) has no cooldown, so the cadence is one letter per 20 minutes. On mainnet the writer loses about two thirds, so it is a last-resort exit rather than an attack; on Sepolia (mintOracleFee) the fee sale buys only the tip, so the conversion costs the 2% trade fee. Consistent with invariants 14 and 15; reported because invariant 1 says PLEA leaves a wallet only after an approval and the threat model does not list this path. No code change is needed if the owner accepts it in writing; the alternative is to keep the tip when a plea gets no verdict, which closes the 20-minute cadence. Merged from audit_math 50fded9e.

### 6. Info: A letter's own fee sale is often the hour's first trade and re-bases the hourly checkpoint, so an APPEAL letter in the same hour can be scored on different P&L and trend facts than the plea it appeals

`src/Letterbox.sol:300`

```
        (id, feePlea) = gate.submitFor(writer, amount, bal, text, flags, feeImd, maxFeePlea);
```

The gate scores a plea on hook.latestPrice(), the price the hour's first trade found (R2-A1-1, documented). submitFor computes the fact score before the fee sale (correct order), but the fee sale is a trade: when it is the hour's first it writes a checkpoint carrying the pre-trade price, i.e. the price left by the writer's own buy a day earlier, above the checkpoint the original was scored on. An APPEAL in the same hour is then scored on the moved checkpoint: the share band is clamped (R6-M-1 holds) but the P&L and trend bands can move, so the appeal's need may differ from the original's. Within the agreed 'facts at submit time from hourly checkpoints' rule and market-direction dependent, so informational: a reader may expect the appeal's need to equal the original's, which holds only when the checkpoint has not moved. Merged from audit_math ab49eeec.
