# Audit report

> PLEA security audit, round 12, area A3: The market: PleaHook. PLEA is a sell-gated meme token on Uniswap v4 paired with IMD: anyone buys, selling needs a plea judged by a 30-seat IdentityMD oracle panel, approved pleas score season points for IMD and PLEA prizes, and every trade pays cashback in staked IMD through imd/acc's Stacker. Solidity 0.8.26, Foundry (cancun, via-IR), a Uniswap v4 hook, Intake v2 callbacks. > Context: PleaHook is a fork of POOL4's CappedBurnHook on the IMD side: IMD as the quote asset, LP fee 0, the hook is the only liquidity provider and its liquidity is locked forever, trims burn 100% of the PLEA and the recovered IMD becomes an IMD-only buy wall below the price. Every trade pays 2.25% inside the swap: 0.5% cashback as staked IMD through imd/acc's Stacker (plain IMD if the credit reverts), 1% to the owner, 0.25% to the season pot (pool liquidity once the Cabal is dead), 0.25% to pool liquidity, 0.25% of the PLEA leg burned. ## Findings

### 1. Info: PAYOUT_RESERVE NatSpec still describes the pre-round-4 rule ('below this much IMD in the PoolManager') while _payFees keys the opening exception on the pool's own IMD plus the buy's fee

`src/PleaHook.sol:83`

```
    /// @dev Below this much IMD in the PoolManager a buy's unfunded payouts join liquidity (2 IMD covers
    /// the 1.75% payouts of the largest buy the launch window allows).
```

The constant's comment says a buy's unfunded payouts join liquidity 'below this much IMD in the PoolManager'. Since the round-3/4 fixes R3-A3-1 and R4-A3-2, _payFees (lines 606-616) never reads the PoolManager's balance for that decision: own = _imdIn(market, priceBefore) + _imdIn(wall, priceBefore) + retainClaims, asClaims = own < out && imd.balanceOf(poolManager) < out, and the exception fires only while asClaims && buy && own + imdFee < PAYOUT_RESERVE. THREAT-MODEL section 3, README 'Fees' (line 193) and the _payFees NatSpec (lines 579-587) state the current rule; the constant's comment contradicts them. On Ethereum the PoolManager holds about 259,490 IMD of other pools, so a reader of the comment would think the exception can never fire, while it is unreachable there for a different reason (asClaims is false). Conversely a first buy into an empty PoolManager whose fee alone is 2 IMD or more pays ERC-6909 claims although the PoolManager holds 'below this much'. Documentation only: cbor_metadata = false and bytecode_hash = none, so the comment changes no byte of the creation code. Merged from four specialists (flow, math, economics, permissions). Fix: reword to 'While this pool's own IMD before the swap (market band, wall, retainClaims) plus the buy's own fee is under this much and the PoolManager cannot pay them, a buy's unfunded payouts join liquidity'.

### 4. Info: _applyCap names the post-swap price priceBefore, while afterSwap and _payFees use that name for the genuine pre-swap price from transient storage

`src/PleaHook.sol:791`

```
        uint160 priceBefore = currentSqrtPriceX96();
```

In _applyCap the local priceBefore is read with currentSqrtPriceX96() after the swap has executed (afterSwap calls _applyCap once the fill is known), so it is the price the swap left; it measures the market's PLEA holdings for the ratchet and the trim and anchors the PriceMoved check after the liquidity removal. afterSwap and _payFees use the same identifier for the pre-swap price carried in T_PRICE_BEFORE. A reader following the cap-ratchet questions can take the trim to be measured against pre-swap holdings; it is measured against post-swap holdings, which is the correct behaviour (a sale's excess exists only after the fill). Naming only, no behaviour or bytecode change. Reported by the math specialist. Fix: rename to priceAfter or spot.

**Reproduction**

Read src/PleaHook.sol:791 against :474-479 and :499-504: in beforeSwap priceBefore = currentSqrtPriceX96() is stored before the swap and reloaded in afterSwap; in _applyCap (called from afterSwap at :568, after the fill) the same name is assigned currentSqrtPriceX96(), the post-swap price. Behaviourally (existing suite, test/full/Hook.t.sol trim tests): after the death a sale that lifts the market's PLEA above inventoryCap is trimmed in the same swap, i.e. held is the post-swap holding; a measurement at the real pre-swap price would have found no excess. No code defect.
