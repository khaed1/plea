# Audit report

> PLEA security audit, round 3, area A3: The market: PleaHook. PLEA is a sell-gated meme token on Uniswap v4 paired with IMD: anyone buys, selling needs a plea judged by a 30-seat IdentityMD oracle panel, approved pleas score season points for IMD and PLEA prizes, and every trade pays cashback in staked IMD through imd/acc's Stacker. Solidity 0.8.26, Foundry (cancun, via-IR), a Uniswap v4 hook, IdentityMD Intake v2 callbacks. This is the mainnet code, rehearsed first on Sepolia (launch.json on this commit has the Sepolia settings). Other areas of the same commit are audited by separate jobs; stay on this one.

## Findings

### 1. High: A router that flash-takes the PoolManager's IMD inside its unlock makes any buy pay no owner, prize or cashback share (the PAYOUT_RESERVE exception is reachable at any pool age)

`src/PleaHook.sol:578`

```
            uint256 pmImd = imd.balanceOf(address(poolManager));
            bool asClaims = pmImd < out;
            // The opening buys: while the PoolManager holds under PAYOUT_RESERVE of IMD (the swapper's
            // input settles after this), a buy's unfunded payouts join pool liquidity. No flag: a dust
            // buy, whatever its fee, cannot use the exception up for the buy that follows it.
            if (asClaims && buy && pmImd < PAYOUT_RESERVE) {
```

_payFees decides whether a buy is one of the 'opening buys' by reading the PoolManager's live IMD balance. Under v4 flash accounting any unlocker may call poolManager.take(IMD, self, balance) before its swap and repay the debt with its swap input at the end of the same unlock, so a router can make the PoolManager hold 0 IMD at the moment afterSwap runs, at any pool age and at no capital cost. The hook then takes the `pmImd < PAYOUT_RESERVE` branch: it emits PayoutsToPool, zeroes cashback, toOwner and toPrize and sends the whole 1.75% IMD fee to retainClaims (the wall). With the balance left between PAYOUT_RESERVE and `out` the same lever forces the ERC-6909 claims path for the owner's and Seasons' shares of any buy (CashbackPaidClaims; the owner needs an unlocking contract to redeem). THREAT-MODEL invariant 19 (every trade through any router pays 0.75% to the owner, 0.25% to the season pot, 0.5% cashback) is broken; section 3 allows the exception only for 'the first fee-paying buy into an empty PoolManager', and the R2-A3-1 fix (round 3) assumed the PoolManager's balance tracks pool age. Economics: a buyer who does this forfeits their own 0.5% sIMD cashback to strip 1.0% of volume from the owner and the season pot (griefing that costs the attacker less than the victims lose), and it is a permanent bypass of the agreed split for anyone who prefers the IMD to sit in the wall (which supports their own PLEA) rather than go to the owner. Invariants checked: 19 (broken by this path), 20, 21, 22 (hold). Fix: base the exception on state no unlocker can move inside a call, e.g. the pool's own IMD (imdInMarket() + the wall's IMD + retainClaims + retainedImd) being under PAYOUT_RESERVE, optionally together with the launch window; with that measure a flash-drained buy simply reverts in the owner's take (the PoolManager has no balance), which only hurts the drainer. Use the same measure for the asClaims decision or pay claims only when the pool's own IMD is short. Do not read imd.balanceOf(poolManager) for either decision.

**Reproduction**

Default launch, 91 minutes after seed (window over). Alice buys 2,000 IMD of PLEA normally: the PoolManager holds ~1,965 IMD. Mallory's router unlocks, calls poolManager.take(IMD, router, imd.balanceOf(poolManager)) (all of it), swaps an exact-input buy of 1,000 IMD with hookData = abi.encode(mallory), then syncs, transfers the swap input plus the borrowed IMD back and settles. Expected (invariant 19, fill = 1,000 - 1,000*175/10,175 = 982.8 IMD): owner +7.371 IMD, Seasons +2.457 IMD, mallory 4.914 sIMD, retainClaims +2.457 IMD. Actual: owner +0, Seasons +0, sIMD 0, PayoutsToPool(14.74e18) emitted and retainClaims +17.2 IMD (the whole 1.75% fee). The control buy without the take pays the owner 7371007371007371007 wei. Run: forge test --match-path test/scratch/FlashDrainPayouts.t.sol (test_flashTakenPoolManagerStripsOwnerPrizeAndCashback fails with 'owner share stripped: 0 != 7371007371007371007'; test_controlBuyPaysEveryShare passes).

### 2. Low: Buys while the Cabal lives return a zero PLEA delta to the swapper, so routers that enforce amountOutMinimum (Universal Router, V4Router) revert for any minimum above zero: buyers through public route

`src/PleaHook.sol:527`

```
                ret = int128(int256(unspecAmt));
```

For an exact-input buy while the Cabal lives, afterSwap takes the whole PLEA output (delivering it as ERC-20 to the trader) and returns unspecAmt as the hook's unspecified delta, so the swapper's own PLEA delta is exactly zero (test/utils/Mocks.sol BuyRouter and MsgSenderRouter document this). Uniswap's V4Router _swapExactInputSingle computes amountOut from that delta and reverts V4TooLittleReceived when it is below amountOutMinimum, and the Universal Router's V4_SWAP actions carry no sqrtPriceLimit, so a buyer through the Universal Router must pass amountOutMinimum = 0 and has no protection against the price moving between quote and inclusion. The PLEA-delta-zero rule is deliberate (invariant 1: no positive PLEA delta leaves the pool while the Cabal lives) and this is not a loss of pool or prize funds; while the Cabal lives only a holder with an approved plea in its 7-minute window can sell into a front-run buy, and after the death the swapper's delta is the real output again (ret = pleaFee), so minimum-output checks work. Not documented in README or THREAT-MODEL ('buy through any router'). Suggested: document that routers must pass amountOutMinimum = 0 and use sqrtPriceLimitX96 for slippage, or let hookData carry a minOut the hook enforces in afterSwap (revert when unspecAmt - pleaFee < minOut), which keeps the delta rule and gives routers an equivalent guard.

**Reproduction**

Cabal alive (default fixture). A router that forwards a user's minimum: in unlockCallback, d = pm.swap(key, {zeroForOne: !pleaIsZero, amountSpecified: -100e18, sqrtPriceLimitX96: MIN/MAX}, abi.encode(user)); pleaDelta = pleaIsZero ? d.amount0() : d.amount1(); require(uint128(pleaDelta) >= minOut). Expected: pleaDelta ~ 17M PLEA for 100 IMD at the 5,700 IMD cap, the check passes for any sane minOut. Actual: pleaDelta == 0 (BuyRouter.unlockCallback takes amountOut == 0 for the payer; the trader's ERC-20 balance moves instead), so any minOut > 0 reverts. Same swap after the Cabal's death: pleaDelta is the output net of the 0.25% burn and the check works.

### 3. Low: The IMD-is-currency0 orientation (pleaIsZero == false) is never executed by any suite: the default Fixture and the Orientation suites both yield pleaIsZero == true, contrary to the Fixture's comment

`test/utils/Fixture.sol:126`

```
    /// @dev Default: IMD sorts below PLEA (IMD is currency0). Orientation tests override this.
```

Fixture.deployImd deploys MockIMD by CREATE before PLEA; in the built suite MockIMD lands at 0x2e234DAe75C793f67A35089C9d99245E1C58470b and PLEA at 0x1d1499e622D69689cdf9004d05Ec547d650Ff211, so PLEA < IMD and hook.pleaIsZero() is true in every suite built on the default fixture. Orientation.t.sol then etches IMD at type(uint160).max, which is the same ordering (PLEA still currency0), so the 'other branch' it promises never runs. Every `!pleaIsZero` branch in src/PleaHook.sol (seed's upper = _alignDown(tick) single-sided band, _pleaIn/_imdIn, _rebalance's band-above-spot placement, _guardFor's tick + 1, _updateWallGuard's mirrored directions, _priceX96's inversion, _checkMaxBuy on an exact-out buy, _removeLiquidity's mapping) and CabalGate.unlockCallback's delta mapping ship untested. On mainnet IMD is 0xd34a99bc0f67ae1bbd63c660e6d0b0dd03e263b7 and PLEA's address is whatever the launch factory's CREATE yields, so the untested ordering has a real chance (~17%) of being the live one. THREAT-MODEL invariant 19's 'both currency orderings' is asserted by no test. I reran HookTest (20 tests) and HookRevisionTest (13 tests) with IMD etched at 0x1234 (IMD currency0, test/scratch/LowImdOrientation.t.sol, which asserts !hook.pleaIsZero()): all 33 pass, so this is a coverage defect, not a demonstrated logic defect.

**Reproduction**

Probe (test/scratch/OrientationProbe.t.sol, a contract inheriting Fixture and one inheriting PleaIsZeroFixture, logging the addresses): default fixture plea 0x1d14...F211, imd 0x2e23...470b, pleaIsZero true; Orientation fixture plea 0x1d14...F211, imd 0xFFfF...FfFF, pleaIsZero true. Expected per the Fixture comment and Orientation.t.sol's header: one of the two covers IMD as currency0. Actual: both cover PLEA as currency0; `assertFalse(hook.pleaIsZero())` fails in both. Fix: correct the Fixture comment and make Orientation.t.sol's second fixture etch IMD at a LOW address (e.g. deployCodeTo("Mocks.sol:MockIMD", "", address(0x1234))), assert !hook.pleaIsZero(), and run the hook, gate, revision, AuditRound1, invariant and adversarial suites under it.

### 4. Info: The inventory cap also ratchets down on sells that leave the market under the cap, not 'only ever follows buys' as the NatSpec and README say

`src/PleaHook.sol:88`

```
    /// fastest; the daily allowance is fixed at seed (`capDecayPerDay`). It only ever follows buys.
```

_applyCap runs unconditionally at the end of every afterSwap and its ratchet branch is `held < inventoryCap` with no buy condition, so a sell whose PLEA does not lift the market's holdings back above the cap lowers the cap toward `held` by the banked daily allowance as well. The pace bound (at most (seeded - 900k)/15 per day, never below the holdings or 900k) still holds, so invariant 21 is not broken; the comment and README describe a narrower behaviour than the code. Documentation only: reword to 'follows trades down while the market holds less than the cap', or gate the ratchet branch on `buy` if the narrower behaviour is intended.

**Reproduction**

Default fixture: buy(alice, 2_000e18) (holdings fall well below the cap; the cap ratchets by the banked allowance), skip(1 days), then a gate sell (or a router sell after the death) of 1,000 PLEA that leaves pleaInMarket() < inventoryCap(). Expected per the comment: the cap unchanged by a sell. Actual: inventoryCap() falls by min(one day's allowance, cap - held) in that sell's afterSwap and CapRatcheted is emitted.

### 5. Info: The sell path passes gross output plus the fee as the seller's IMD figure to _updateBasis (the sell branch ignores it today)

`src/PleaHook.sol:541`

```
            _updateBasis(trader, buy, imdBasis + imdFee, buy ? pleaAmt - pleaFee : pleaAmt + pleaFee);
```

For a buy, imdBasis + imdFee is what the trader paid (the pool's fill plus the fee), the right cost basis. For a sell, imdBasis is the pool's gross IMD output (unspecAmt) and imdFee is the 1.75% taken from it, so imdBasis + imdFee is the gross output plus the fee while the seller received imdBasis - imdFee. The sell branch of _updateBasis never reads grossImd (it reduces pleaHeld / imdSpent proportionally), so basisOf is correct today; the value is a latent trap for any future change that reads it on the sell branch (a realised-P&L figure). No invariant affected.

**Reproduction**

Alice sells X PLEA through the gate; the pool pays U IMD gross; imdFee = U*175/10000; alice receives U - imdFee. afterSwap calls _updateBasis(alice, false, U + imdFee, X). Expected (if the figure were used): U - imdFee. Actual: U + imdFee, 3.5% above what she received; basisOf(alice) is unchanged by it.
