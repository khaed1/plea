## Findings

### 1. Low: Letterbox validates its fee-token settings against PleaLaunch, never against the gate that pulls the fee: two manifests pass the constructor and register a Letterbox that can never take a letter and c

`src/Letterbox.sol:167`

```
        if (!mint_ && oracleAsset_ != imd_) revert OracleAssetNotImd();
```

Merged from the flow specialist (mint && oracleAsset == imd) and the economics specialist (PleaLaunch's oracleAsset != the gate's); both reproduced, one root cause and one fix. The Letterbox reads `oracleAsset` and `mintOracleFee` from PleaLaunch (manifest arguments 10 and 11) and the constructor checks them only against PleaLaunch's own `imd` (lines 166-167). The gate has its own immutable `oracleAsset` (CabalGate argument 3) and `_ask` (CabalGate.sol:427) pulls the 0.5 IMD oracle fee from the Letterbox in THAT token. Nothing on chain ties the two together, and one combination the constructor does accept is internally broken: (1) `mintOracleFee = true` with `oracleAsset == imd`: `_approveGate` (lines 355-358) approves the gate for 0.5 on `oracleAsset` and then for the wall share (0 for a plea, 0.35 for an appeal) on `imd`, the SAME token, so the second write overwrites the first and `_ask` reverts ERC20InsufficientAllowance(gate, 0, 0.5e18); (2) PleaLaunch names a fee token the gate does not use (for example the pool IMD with mint = 0, which passes line 167): the Letterbox approves and funds the wrong token and `_ask` reverts the same way. In both cases `deployLetterbox` succeeds and `PLEA.setLetterbox` registers the Letterbox, after which every letter, `plead` and `appealAuto` reverts for the life of the launch: the Letterbox is committed by hash, `deployLetterbox` is one-shot (`LetterboxAlreadyDeployed`), `setLetterbox` is one-shot (`AlreadySet`) and PleaLaunch's settings are immutable. Letters and the site's auto-sell box are the whole loss; the gate's direct `submitSell` still works and no funds are at risk. The committed Sepolia manifest is consistent (gate arg 3 and PleaLaunch arg 10 are both 0x44a1...F89A, mint = 1, and test/LaunchManifest.t.sol pins them), so there is no impact today; the mainnet manifest on the `mainnet` branch is a second hand-edited copy where the same two arguments must agree and mint must be 0, and the Letterbox is deployed after the five-contract transaction, so the launch rehearsal cannot catch it. Severity Low per section 4 (a missing check with no impact today). Fix, preserving behaviour: in the constructor read the gate's token (`CabalGate(l.gate()).oracleAsset()`) and refuse a PleaLaunch `oracleAsset` that differs, and refuse `mint_ && oracleAsset_ == imd_` (or, equivalently, approve ORACLE_FEE + wall in one write when the two tokens are the same address). The attached test accepts either a constructor refusal or a working letter and fails on the code as it is. Invariants checked for this area: 1 (PLEA paths while the Cabal lives), 14 (Letterbox custody: escrows + tips, deliver/settle once, window, strands), 15 (letter fees, floors, flags, mint vs buy), 16 (selectors, LetterTooLong, non-reentrancy), 17 (launch: commitments, CREATE2, seed, clock, gas: test/LaunchManifest.t.sol passes), 18 (distributor); R1-A2-1..7 regression tests in test/AuditRound1.t.sol, test/Letterbox.t.sol, test/AppealRounding.t.sol, test/Launch.t.sol, test/Token.t.sol, test/Distributor*.t.sol and test/MainnetGuard.t.sol all pass on this commit.

**Reproduction**

State: the five launch contracts deployed on any chain id other than 1 (the proof uses 11155111) with either (1) PleaLaunch oracleAsset = the pool IMD and mintOracleFee = true (the gate's oracleAsset also the pool IMD), or (2) the gate's oracleAsset = a separate fee token and PleaLaunch oracleAsset = the pool IMD with mintOracleFee = false. Steps: anyone calls PleaLaunch.deployLetterbox(committed creation code): succeeds, PLEA.letterbox is set. deployHook, seed, a wallet buys 50 IMD of PLEA, a day passes, the wallet sends any letter text as raw input data (or calls plead / appealAuto). Expected: a plea is escrowed and the 0.5 fee reaches the Intake (or the constructor refuses the manifest and nothing is registered). Actual: the call reverts with ERC20InsufficientAllowance(gate, 0, 500000000000000000) raised in CabalGate._ask (trace for case 1: approve(gate, 5e17) then approve(gate, 0) on the same token); deployLetterbox again reverts LetterboxAlreadyDeployed and PLEA.setLetterbox reverts AlreadySet. ### 2. Info: THREAT-MODEL invariant 15 still bounds an appeal's letter fees by "the appeal's own amount"; the code (R1-A2-3), FINDINGS.md and README bound them by the original plea's amount

`src/Letterbox.sol:341`

```
        if (maxFeePlea * BPS > bal * MAX_FEE_SHARE_BPS && maxFeePlea > originalAmount) {
```

Merged from the flow and economics specialists (same observation). audit/THREAT-MODEL.md section 2, invariant 15 (line 54) reads "never more than 10% of the balance (an appeal: or the appeal's own amount)", and this task's brief repeats it ("an appeal up to its own amount"). After the round 1 fix R1-A2-3 the code at line 341 compares `maxFeePlea` with `originalAmount` (the original plea's amount), not with the clamped appeal amount, and FINDINGS.md R1-A2-3 and README.md line 92 ("an appeal's fees may instead go up to the original plea's amount") describe it that way. The two bounds differ: the original's amount is always at least the clamped appeal's (the same-share clamp shrinks the appeal by the first fee sale's share), so the code admits appeals the threat model's wording would refuse. Section 2's bold numbers are what auditors are told to check and a changed agreed number is a finding, so the ledger and the invariant should say the same thing. No funds are at risk beyond the agreed fees: the fee sale is still capped at the snapshot value + 10% of the IMD bought (about 1.21 IMD worth on mainnet) and unspent PLEA comes back; the relative bound only decides which small balances may appeal by letter. Fix: reword invariant 15 (and the brief) to "or the original plea's amount", or, if the threat model is what was agreed, revert R1-A2-3 to the appeal's own amount and re-accept its original finding.

**Reproduction**

Compare audit/THREAT-MODEL.md line 54 ("an appeal: or the appeal's own amount") with src/Letterbox.sol line 341 (`maxFeePlea > originalAmount`), README.md line 92 and FINDINGS.md R1-A2-3. Mainnet fee path (test/AuditRound1.t.sol test_aSmallWriterCanAppealByLetterOnMainnet, which passes on this commit): bob buys 50 IMD, alice buys 8.7 IMD of PLEA, a day passes, alice pleads 15% by letter (fees 0.75 IMD + 10% = 0.825 IMD worth <= 10% of about 8.3 IMD), the panel scores 0, alice sends `APPEAL ...`: the balance is now worth about 7.5 IMD, the appeal fees 1.1 IMD + 10% = 1.21 IMD worth, the same-share clamp puts the appeal at about 1.11 IMD worth. Under invariant 15 as written (10% of the balance = 0.75, or the appeal's own amount = 1.11) the fees must be refused with FeeTooHigh; under line 341 (or the original plea's amount, about 1.24 IMD worth) the appeal is accepted and escrowed. Actual: accepted (the test asserts it).

### 3. Info: deployHook's address is chosen by whoever calls first with any flag-valid salt, not fixed by the commitment as the NatSpec and README say

`src/PleaLaunch.sol:25`

```
/// the committed code, so front-running any of these calls changes nothing. A zero Tribunal hash
```

From the permissions specialist; reproduced. PleaLaunch commits to the hook's init code hash, but `deployHook(salt, initCode)` (line 113-116) accepts any caller's salt whose CREATE2 address carries exactly the FLAGS bits. The resulting address is therefore not determined by the commitment: whoever calls first picks it. A front-runner who sees the team's MineSalt broadcast, or simply calls earlier with another flag-valid salt, deploys the same code at a different address; the team's own deployHook then reverts HookAlreadyDeployed. The code, the owner baked into the init code, the 82/6/12 mint and every on-chain reader (PLEA.hook(), the gate, Seasons and the Letterbox all read plea.hook() at call time; seed reads `hook`) are unaffected, so there is no loss and no permission bypass; the effects are an announced hook address that is wrong and anything off chain that pre-computed the pool key from the mined salt (site config, explorer links, verification scripts) pointing at the wrong contract. The Letterbox and the Tribunal use salt 0, so their addresses are fixed; only the hook's is not. This contradicts the sentence at line 25 ("Every result is fully determined by the committed code, so front-running any of these calls changes nothing") and README step 3 ("the result is fixed whoever calls it"). Info: documentation and operations. Fix: either reword the NatSpec and README to say the hook's address depends on the first caller's salt (any flag-valid address is acceptable), or, if the site needs the address in advance, commit to the salt as well (an immutable chosen off chain before the launch, since the init code hash is known then) and drop the salt argument.

**Reproduction**

State: the five launch contracts deployed, hook not yet deployed. The team mines salt S with predict(S) & FLAG_MASK == FLAGS and announces predict(S). A stranger finds the next flag-valid salt S' > S and calls deployHook(S', initCode) first. Expected per line 25: the hook lands on the announced address. Actual: the hook is at predict(S') != predict(S), plea.hook() == predict(S'), PLEA minted 820,000,000e18 to it, and the team's deployHook(S, initCode) reverts HookAlreadyDeployed. Verified with test/scratch/JudgeA2.t.sol JudgeHookSaltTest.test_aStrangerPicksAnotherFlagValidSalt on this commit (passes: all four assertions hold).
