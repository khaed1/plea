# Audit report

> PLEA security audit, round 2, area A1: The game: gate, Tribunal, seasons. PLEA is a sell-gated meme token on Uniswap v4 paired with IMD: anyone buys, selling needs a plea judged by a 30-seat IdentityMD oracle panel, approved pleas score season points for IMD and PLEA prizes, and every trade pays cashback in staked IMD through imd/acc's Stacker. Solidity 0.8.26, Foundry (cancun, via-IR), a Uniswap v4 hook, IdentityMD Intake v2 callbacks. This is the mainnet code, rehearsed first on Sepolia (launch.json on this commit has the Sepolia settings). Other areas of the same commit are audited by separate jobs; stay on this one.

## Findings

### 1. Low: The hourly reference (24h trend and P&L bands) moves one second after a pump placed at the end of an hour, not after an hour of holding as README and THREAT-MODEL section 3 state

`src/CabalGate.sol:282`

```
        else if (latest > ago * 102 / 100) score += 9;
```

Merged from audit_math (info) and audit_economics (medium): one mechanism. PleaHook._checkpoint (src/PleaHook.sol:1009-1019) writes, once per hour, the price the hour's FIRST trade found, i.e. the price the previous hour's LAST trade left. CabalGate._factScoreAt reads that newest checkpoint as `latest` for both the 24h-trend band (line 282: up 9 / flat 5 / down 0) and the P&L band (line 273). So a buy in the last second of hour H (which sets no checkpoint of its own once any trade already happened in H) followed by any dust trade in the first second of hour H+1 makes the pumped spot the reference for every plea scored in H+1, including the pumper's own plea in the same transaction as the dust trade. Nothing is held for an hour. README 'The fact score' (line 111: 'a pump still has to be held through the hour before') and THREAT-MODEL section 3 ('a pump must be held through the previous hour to move the fact score') state a stronger guarantee than the code gives. Severity: Low, not the specialist's Medium. No agreed number changes and invariant 3 holds as written (hourly checkpoints, the price an hour's first trade found, never spot); the effect is bounded to the fact score (at most +9 trend points, i.e. a need 4-9 lower for everyone pleading that hour, and a P&L band shift for sellers near the loss boundary), the panel still scores the plea, no pot or sale is touched, and the pump costs the 2% fee on a buy of about 1% of pool depth plus PLEA that can only leave through the gate (max 50% / 2.5M per plea). The symmetric direction (an approved seller timing a legitimate sale at HH:59:59, then a dust buy at HH+1:00:00, lowering every other pleader's trend to 'down') follows from the same code but was not separately reproduced here. Fix: either reword README line 111 and THREAT-MODEL section 3 to 'the next hour's checkpoint is the price the previous hour's last trade left, so a pump must only be the last trade before the boundary', or, if an hour of holding is wanted, change the checkpoint rule (e.g. record the price the hour's first trade found only when it agrees within tolerance with the price that hour's own first trade found an hour earlier, or use the older of the two newest hourly checkpoints). The second option is a contract change outside the agreed numbers and needs the owner's decision.

**Reproduction**

Fixture (test/utils/Fixture.sol, Sepolia settings, 5,700 IMD cap, 91 minutes after seed). alice buys 20 IMD, bob buys 2,000 IMD (alice at a deep gain so her P&L band is stable), skip 1 hour, carol buys 1 IMD (checkpoint of the post-bob price), skip 24 hours, keepAlive(alice). Warp to 2 seconds before the next hour boundary: carol buys 1 IMD (hour H's checkpoint = the quiet price; latestPrice <= price24hAgo * 1.02: flat). gate.factScore(alice, balanceOf(alice)/10) == 26 (share 16 + hold 2 + gain 3 + flat 5). At HH:59:59 carol buys 250 IMD: hook.latestPrice() is unchanged (the pump sets no checkpoint). Warp to HH+1:00:00, carol buys 1 IMD: hook.latestPrice() is now the pumped price (> 1.02 x price24hAgo) and gate.factScore(alice, balanceOf(alice)/10) == 30 (trend 9). Expected per README line 111 / THREAT-MODEL section 3: 26, unchanged, because the pump was held one second and not through an hour. Actual: 30. Reproduced by the judge with the specialist's test placed at test/scratch/TrendBoundary.t.sol (forge test --match-path test/scratch/TrendBoundary.t.sol fails with '30 != 26'). Its source follows; no proof is attached because the expected fix may be the documentation, which no test can be held to:

// SPDX-License-Identifier: MIT
pragma solidity 0.8.26;

import {Fixture} from "../utils/Fixture.sol";

/// @dev Audit round 2, A1: the 24h trend fact reads the hour's first-trade checkpoint. A buy in the
/// last second of hour H followed by any trade in the first second of hour H+1 writes the pumped
/// price as H+1's checkpoint: the pump is held for one second, not "through the previous hour".
contract TrendBoundaryTest is Fixture {
    function test_pumpHeldOneSecondAcrossTheHourMovesTheTrendFact() public {
        // Day-old history: a trade now, then 24 hours of quiet (keepAlive verdicts need no trade).
        buy(alice, 20e18);
        buy(bob, 2_000e18); // alice now sits at a deep gain (P&L band 3, robust to a few percent)
        skip(1 hours);
        buy(carol, 1e18); // next hour's checkpoint: the post-bob price (today's reference)
        skip(24 hours);
        keepAlive(alice);
        // Align to one second before the next hour boundary.
        uint256 t = vm.getBlockTimestamp();
        uint256 nextHour = (t / 1 hours + 1) * 1 hours;
        vm.warp(nextHour - 2);
        buy(carol, 1e18); // hour H's checkpoint: the quiet pre-pump price
        vm.warp(nextHour - 1);
        uint256 agoBefore = hook.price24hAgo();
        uint256 latestBefore = hook.latestPrice();
        assertGt(agoBefore, 0, "24h history exists");
        assertLe(latestBefore, agoBefore * 102 / 100, "flat before the pump");
        uint8 flatScore = gate.factScore(alice, plea.balanceOf(alice) / 10);
        // Carol pumps at HH:59:59 (this hour's checkpoint already holds the pre-pump price).
        buy(carol, 250e18);
        assertEq(hook.latestPrice(), latestBefore, "the pumping trade sets no checkpoint of its own");
        // One second later, any dust trade checkpoints the pumped price for the new hour.
        vm.warp(nextHour);
        buy(carol, 1e18);
        uint256 latestAfter = hook.latestPrice();
        assertGt(latestAfter, agoBefore * 102 / 100, "the new checkpoint is the pumped price");
        uint8 pumpedScore = gate.factScore(alice, plea.balanceOf(alice) / 10);
        // THREAT-MODEL section 3 / README: "a pump must be held through the previous hour to move the
        // fact score". Here it was held for one second. Expected: the fact score is unchanged.
        // Actual on this code: the trend fact moves from flat (5) to up (9) for every pleader.
        assertEq(uint256(pumpedScore), uint256(flatScore), "a pump held one second must not move the fact score");
    }
}

### 2. Info: Every fresh buyer scores 'at a loss' (13) in a flat market, because the basis is gross of fees and the checkpoint is the pre-trade price

`src/CabalGate.sol:273`

```
            if (value < spent) {
```

From audit_economics (info), reproduced. PleaHook._updateBasis (src/PleaHook.sol:690-698) adds grossImd, what the buyer paid including the 2.0% IMD fee, to imdSpent, and the PLEA received is net of the 0.25% burn and the buyer's own price impact. CabalGate compares heldPlea x latestPrice (an hourly checkpoint, the price a trade FOUND) with that gross spend, so in a market that has not moved since the buy the value is about 1.5-3% below the spend and the P&L band is 'at a loss' (13) rather than 'gain <= 50%' (8) until the checkpoint rises past the fee margin. The README's calibration sentence ('A fresh buyer selling 15% at a loss needs 37', line 58) reads as one scenario but is the default for every fresh buyer, and the band flips on a sub-3% move either way (which is what makes the Low finding above move a seller's P&L band as well). No agreed number changes; the 'at a loss' band is wider than its name suggests. Fix: document it in README 'The fact score' (loss means a loss on the gross spend, fees included), or, as a design change for the owner, compare value with the spend net of the fee.

**Reproduction**

Fixture: buy(bob, 5 IMD); buy(alice, 20 IMD); skip 1 hour; buy(carol, 1 IMD) (checkpoints the post-buy price); skip 23 hours; keepAlive(bob). hook.basisOf(alice) = (spent 20e18, held 3,405,853e18, avgBuyTime); hook.latestPrice() = 458,011,283,640,514,846,888,253 (X96); value = held x latest / 2^96 = 19.689e18 < 20e18 although no trade since alice's buy lowered the price (latest is above price24hAgo 453,250,947,750,297,829,343,545). gate.factScore(alice, balanceOf(alice)/10) == 36 = share 16 + hold 2 + at a loss 13 + flat 5. Expected by the README's reading of 'at a loss' as a loss on the market price: 31 (gain <= 50%: 8). Actual: 36. Judge's probe test/scratch/JudgeProbe.t.sol test_freshBuyerLossBand passes asserting value < spent and factScore == 36.

### 3. Info: Invariant 4's 'for the exact rebuilt question' rests on the Intake's pairing, not on an on-chain check: the gate never compares a.questionHash with its own question

`src/CabalGate.sol:516`

```
        _verifyAttestation(a, signature);
        _consume(a.requestId);
```

Documentation precision for THREAT-MODEL invariant 4 ('A verdict is accepted only from the oracle signer, for the exact rebuilt question of the pending plea'). onOracleResult binds the answer to the plea through pleaOfIntake[intakeId] (the Intake's id of the request the gate itself paid for) and the signature over the gate's domain; a.questionHash is signed but never compared with the question the gate built, and the Tribunal's onOracleResult does the same. With a relative window ({"hours":1}) the hash cannot be computed on chain (the oracle-consumer reference says so and says the pairing of an answer to the intake request is the writer's), so this is the protocol's trust assumption on the Intake and its writer (THREAT-MODEL section 1 lists the Intake as a trusted contract), not a bypass: no outsider can present an answer for an intakeId the gate created, and a stranger's own request lands on UnknownRequest. Reported so that the invariant's wording matches what the code enforces: 'for the request id the gate paid for, as paired by the Intake'. No code change is proposed; if the owner wants the on-chain binding, the body would have to use an absolute block window and store the computed questionHash per plea, which costs gate bytecode (83 bytes of headroom).

**Reproduction**

Every verdict test in the repository already shows it: test/utils/Fixture.sol attestation() signs questionHash = keccak256("question") for every plea and every objection, and CabalGate.onOracleResult / Tribunal.onOracleResult accept it (e.g. test/Gate.t.sol, 29 passing tests at this commit). Expected by the invariant's wording: an attestation whose questionHash is not keccak-256 of the gate's canonical question document is refused; actual: accepted, because only the Intake's intakeId and the signer are checked.
